# Сервис кикшеринга «ВышКат»
Домашнее задание №1 по КПО (ФКН ВШЭ)

Консольное приложение для учёта самокатов, велосипедов и сопутствующего инвентаря в парке проката ВШЭ. Включает техосмотр перед приёмом техники, подсчёт суммарного суточного энергопотребления, фильтрацию для новичков и балансовый учёт вещей.

Стек: **Go 1.22**, без внешних зависимостей.

## Применение SOLID в проекте

- **Single Responsibility (SRP):**  
  Каждый пакет занят своим делом. `transport.go` просто хранит поля техники, `inspector.go` проверяет состояние и даёт вердикт, `memory.go` хранит данные и следит за уникальностью инвентарных номеров, `fleet.go` связывает всё это в бизнес-сценарии, а `cli.go` выводит текст в терминал.

- **Open/Closed (OCP):**  
  Если нужно добавить новый транспорт (например, гироскутер), достаточно описать новую структуру, реализующую интерфейс `Transport`. Методы сервиса `FleetService` и подсчёт энергии трогать не придётся.

- **Liskov Substitution (LSP):**  
  Все виды транспорта (`KickScooter`, `ElectricBike`, `Bicycle`) взаимозаменяемы в сервисе. Механический велосипед без мотора ведёт себя корректно: при расчёте энергии он просто игнорируется, программа не падает.

- **Interface Segregation (ISP):**  
  Вместо одного большого интерфейса сделаны три маленьких: `InventoryItem` (всё, у чего есть инвентарный номер), `EnergyConsumer` (только те, кто кушает батарею) и `BeginnerFriendly` (прокатная техника с оценкой сложности). В итоге шлему не нужно прикручивать метод расхода электричества, а зарядному шкафу - методы управления поездкой.

- **Dependency Inversion (DIP):**  
  `FleetService` не привязан намертво к конкретному сервисному центру или хранилищу в памяти, а принимает интерфейсы `Inspector` и `FleetRepository`. За счёт этого в тестах настоящий техосмотр легко подменяется на мок.

## DI-контейнер

Сделан простой самописный Builder (`internal/di/container.go`) без сторонних тяжелых библиотек:
- `di.NewDefaultContainer()` — собирает всё по умолчанию для обычного запуска.
- `di.NewContainerBuilder().WithInspector(mock).Build()` — позволяет подсунуть мок в тестах.

## Ответы на обязательные вопросы из ТЗ

### 1. Какой принцип SOLID применён наиболее явно и где?
Наиболее наглядно применен **Interface Segregation (ISP)** в файле `internal/domain/interfaces.go`.  
Интерфейсы разделены: `InventoryItem`, `EnergyConsumer` и `BeginnerFriendly`.  
Поэтому:
- Шлем числится на балансе с инвентарным номером, но не реализует методы расхода энергии;
- Обычный велосипед является транспортом для новичков, но не является потребителем электричества;
- Зарядный шкаф потребляет энергию (и входит в общий суточный расход парка), но не является транспортом.

### 2. Какой принцип сознательно ограничен / «почти нарушен» и почему это приемлемо?
Принцип **Open/Closed (OCP)** ограничен в консольном меню `internal/app/cli.go` (в методе `handleRegisterTransport`).  
Там выбор вида транспорта сделан через обычный `switch-case`. При добавлении нового транспорта придётся дописать ещё одну ветку в меню.  
Это сделано осознанно: в домене и сервисах OCP соблюдён полностью. Расписывать в данном проекте динамическое распознавание ради консоли - оверинжиниринг.

### 3. Что сломается (или не сломается) при добавлении нового вида транспорта, сотрудника или склада запчастей?
- **Новый транспорт:** Ничего не сломается. Объявляем структуру с методами `domain.Transport` (и `EnergyConsumer`, если электрический). Всё сразу заработает в `FleetService`.
- **Сотрудник:** По условию сотрудники на баланс не ставятся. Поэтому они не должны реализовывать `InventoryItem`. Для них заводится отдельный тип и свой сервис, логика автопарка никак не сломается.
- **Склад запчастей:** Если запчасть штучная с номером (например, аккумулятор), она реализует `InventoryItem` и ставится на баланс через `RegisterItem()`. Для коробок с болтами и мелких расходников нужен отдельный складской сервис, автопарк это тоже не затронет.

### 4. Какой тест фиксирует решение техосмотра и/или правило «для новичков»; как подменяется зависимость?
1. **Решение техосмотра:**
    - В `internal/service/fleet_test.go` тест `TestFleetService_RegisterTransport_Rejected_UnderCondition` проверяет, что если техосмотр отклонил самокат, тот не добавляется в парк (`len == 0`).
    - Подмена зависимости: написан тестовый `MockInspector`, который реализует интерфейс `service.Inspector`. В поле `ShouldApprove` задаётся нужный вердикт. В тесте `TestFleetService_DI_MockSubstitution` показано, как он прокидывается через DI-билдер.
2. **Правило «для новичков» (оценка $\ge 6$):**
    - Тест `TestFleetService_GetBeginnerFriendlyTransports` в том же файле регистрирует технику с оценками 8, 4, 6, 3 и проверяет, что в список попали только устройства с оценками 8 и 6.

## Использование ИИ

В проекте использовался ИИ для автоматизации стандартных и рутинных задач:

1. **Юнит-тесты:**  
   Почти весь объём тестов сгенерирован с помощью ИИ. По описанию методов были сгенерированы тест-кейсы для проверки граничных значений (порог 70% на техосмотре, проверка оценки новичков $\ge 6$, отказ при нулевом потреблении, проверка дублей инвентарных номеров), а также заготовка для `MockInspector` и названия-примеры инвентарных объектов.
2. **Шаблонный код:**  
   ИИ сгенерировал базовые структуры в `domain` (поля, геттеры, конструкторы `New...`) и примитивные методы хранения данных в мапах для `repository`.
3. **Вывод в терминале:**  
   Форматирование таблиц в `cli.go` (выравнивание строк по колонкам) также отдано ИИ.
